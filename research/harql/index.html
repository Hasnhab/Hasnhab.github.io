HARQL / TECHNICAL RESEARCH

From Regex to Reconstruction: The Engineering Evolution of HarQL

A Technical History of Reverse-Engineering Hidden GraphQL Operations from Obfuscated Client-Side JavaScript

Hasan Habeeb Version 1.0 Published 2026-08-14

Abstract

When GraphQL introspection is disabled in a production environment, conventional schema-discovery techniques lose much of their value. The absence of introspection, however, does not mean that a particular client implementation is unaware of the API structure it needs to invoke. A web application still has to retain enough operation-specific information to construct the requests required by its implementation.

HarQL was developed around that observation. Its purpose is to recover GraphQL operation metadata from JavaScript artifacts generated for Meta's web applications using Relay, and to combine that information with values observed in live traffic. What began as a small regex-based experiment developed into a broader reverse-engineering workflow incorporating module correlation, Relay artifact analysis, runtime observation, value matching, request reconstruction, and Burp Suite integration.

This article documents that development in technical rather than promotional terms. It examines the implementation choices that proved useful, the heuristics that did not survive, the architectural costs introduced by successive designs, and the limitations that remain. The resulting picture is less a story about a single extraction technique than an account of how practical reverse engineering evolves when the target client is large, generated, aggressively minified, and backed by a GraphQL service whose introspection interface is not available to the researcher.

1. The Problem

GraphQL introspection provides one of the most direct ways to query the type system exposed by a GraphQL service. In a deployment where introspection is disabled or otherwise unavailable to the researcher, that source of schema information is no longer directly accessible. For security research, API analysis, and protocol reconstruction, the immediate consequence is reduced visibility into the operations exposed by the application.

The server-side restriction does not eliminate the client's need for that knowledge.

A browser application cannot construct the requests required by a particular GraphQL client implementation without retaining enough operation-specific information to do so. Depending on the client and transport conventions involved, that information may include an operation name or persisted-operation identifier, variable definitions or values, and the representation required by the application's request format.

That information is therefore already present somewhere in the client.

For the Meta web applications examined in this research, much of that information was embedded in large JavaScript bundles produced by the application's Relay-based compilation pipeline. The relevant information is distributed across generated modules and artifacts rather than presented as a clean, queryable schema. Minification further removes the syntactic cues that would normally make the relationships obvious to a human reader.

The engineering problem is consequently one of recovering structure from generated client code.

HarQL was built to explore that problem in practical terms.

2. Research Question

The investigation began with a simple question:

How does the Meta web client examined in this research retain enough information to construct a GraphQL operation when the tested service does not expose its schema through introspection?

The initial hypothesis was that the mapping between readable operation names and the opaque doc_id values observed in the Meta application's requests would be represented somewhere in the JavaScript artifacts delivered to the browser.

That hypothesis proved productive.

Inspection of Meta's bundles revealed recurring numeric identifiers associated with Relay operation modules. Once those identifiers could be correlated with observed requests, a broader set of questions followed:

  • Where are the operation names encoded?
  • Where do variable definitions live?
  • How are defaults represented in minified compiler output?
  • Can information split across several generated artifacts be correlated?
  • Can static variable definitions be enriched with values observed during normal application traffic?
  • Can the resulting data structure be used to reconstruct a request rather than merely enumerate identifiers?

HarQL's architecture grew in response to those questions.

It is best understood as a specialized reverse-engineering system for Relay-generated GraphQL artifacts rather than as a general-purpose GraphQL scanner.

3. Stage 1 — Finding doc_id

The first useful results came from a simple local analysis idea: inspect JavaScript files already collected in a local directory and determine whether the opaque doc_id values seen in live GraphQL requests could be located reliably inside the corresponding client-side JavaScript.

Long numeric strings appeared repeatedly around assignments of the form: 

e.exports = "..."

Some of those values could be correlated with the doc_id parameter observed in GraphQL-related requests generated by the Meta web client. That correlation provided the first concrete evidence that the client-side bundles contained the operation identifiers needed to understand the requests.

The initial implementation, stage-01.py, therefore ran as a mitmproxy addon and inspected JavaScript responses as they passed through the proxy. Its core extraction logic used a regular expression: 

doc_id_pattern = re.compile(r'e\.exports\s*=\s*["\'](\d{8,})["\']')

For each match, the script examined a fixed local region of the response and attempted to extract a nearby variable object: 

def extract_variables_nearby(lines, index):
    search_range = lines[max(0, index-20): index+20]
    combined = "\n".join(search_range)
    match = variables_pattern.search(combined)
    if match:
        raw_vars = match.group(1)
        keys = re.findall(r'["\']?([\w_]+)["\']?\s*:', raw_vars)
        return list(set(keys))
    return []

At this point the system was not trying to understand Relay's generated module structure. It was testing whether a recognizable identifier pattern could be located in JavaScript at all, using a simple local scan of previously collected files.

That approach was useful for establishing the signal.

It also exposed the first serious weakness in the extraction strategy. The script associated variables with identifiers based on physical proximity—roughly twenty lines in either direction. That assumption has little meaning once JavaScript has been transformed by a compiler and aggressively minified. A logically related construct may be separated from the identifier by an arbitrary amount of generated code, while an unrelated object may happen to fall within the same textual window.

The first stage therefore established two things at once: doc_id values were recoverable from client-side JavaScript, and naive spatial association was not a dependable way to reconstruct the surrounding operation.

The next step was to use the module structure itself to connect the identifier with the operation it represented.

4. Stage 2 — Correlating Operations

Once doc_id extraction worked, the next practical problem was obvious: an identifier without an operation name had limited analytical value.

With the initial extraction idea established, the investigation then moved from local file analysis into live interception with mitmproxy. The goal of the second stage was to determine how Relay operation modules were named and how those names could be correlated with their numeric exports.

A recurring convention in the examined Meta bundles involved _facebookRelayOperation modules whose names could be associated with numeric exports. The second-stage extractor used the following expression: 

pattern = re.compile(
    r'__d\("([^"]+?)_facebookRelayOperation".*?e\.exports\s*=\s*"(\d+)"',
    re.DOTALL
)

The pattern connected the module definition to its exported identifier and allowed the system to associate an operation name prefix with the corresponding doc_id.

This changed the nature of the tool.

JavaScript responses were now being processed as live artifacts arriving through a proxy rather than as a directory of static files.

The stage also introduced persistent storage: 

repo_json_path = os.path.join(desktop, "relay_repository.json")
session_json_path = os.path.join(desktop, "relay_session.json")

The repository retained information across executions. The session reflected the current capture period. Deduplication used a module-plus-identifier key: 

key = f"{module}:{docid}"
repo_seen = set(f"{m}:{d}" for m, d in repo_entries)

The extracted information was rendered into self-contained HTML output, including client-side export functions for the collected identifiers and module names.

At this point HarQL had acquired something closer to an operation catalog.

The variable-extraction heuristic from the initial script was deliberately not carried forward. Once the project moved into live module-level analysis, the fixed line-based search looked increasingly like a source of false associations rather than a reliable way to establish relationships between generated artifacts.

That decision was important.

The project was beginning to distinguish between a textual coincidence and an actual relationship in generated code.

The second-stage system could identify operations and their identifiers, but it still knew little about the arguments required to invoke those operations. That gap became the focus of the next stage.

5. Stage 3 — Recovering Variables

The Relay-generated JavaScript artifacts examined in the Meta client contained several representations of related information for the same logical operation. Variable information can appear in .graphql artifacts, entrypoint modules, and related generated structures.

Stage 3, implemented in graphql_harvester.py, introduced extraction logic specifically designed around those conventions.

The harvester first isolated individual __d() module blocks: 

MODULE_BLOCK_RE = re.compile(
    r'__d\(\s*"([^"]+)"\s*,.*?\(function\([^\)]*\)\s*\{\s*(.*?)\s*\}\s*\)\s*,.*?\)\s*;',
    re.S
)

This was a meaningful improvement over the earlier line-window heuristic. Instead of asking what happened to be close to doc_id, the extractor first established a module boundary and then reasoned about the contents of that module.

`.graphql` artifacts

The first extraction path targeted LocalArgument structures observed in the Relay-generated artifacts used by the examined Meta client: 

LOCAL_ARG_BLOCK_RE = re.compile(
    r'\{[^{}]*kind\s*:\s*"LocalArgument"[^{}]*\}',
    re.S
)

NAME_IN_BLOCK_RE = re.compile(r'name\s*:\s*"([^"]+)"')

DEFAULT_IN_BLOCK_RE = re.compile(
    r'defaultValue\s*:\s*([^,\}]+)'
)

This allowed the harvester to recover variable names and associated default expressions from generated argument definitions.

`.entrypoint` artifacts

A second path handled entrypoint modules in the examined client artifacts that reference parameter modules and expose variable objects: 

ENTRYPOINT_PAIR_RE = re.compile(
    r'parameters\s*:\s*\w\(\s*"([^"]+)"\s*\)\s*,[\s\S]*?variables\s*:\s*\{(.*?)\}',
    re.S
)

VAR_KEY_RE = re.compile(
    r'([A-Za-z_][A-Za-z0-9_]*)\s*:'
)

This provided an alternative route to the same variable information when the first artifact type was unavailable or incomplete.

Full-text $Parameters extraction

A broader search over $Parameters structures served as a fallback when the more targeted artifact-level approaches failed.

The overall strategy was deliberately redundant.

Generated client code often contains several overlapping representations of the same semantic information. A reverse-engineering tool can exploit that redundancy instead of assuming that one artifact will always contain the complete answer.

6. Default-Value Normalization

Variable names alone do not say much about the values an operation expects.

The next refinement was to normalize default expressions observed in Meta's generated client code.

The helper _normalize_default_token() handled common minified representations: 

def _normalize_default_token(token: str):
    if token is None:
        return None
    s = token.strip()
    if s == "!0": return False
    if s == "!1": return True
    if s.lower() == "null": return None
    if (s.startswith('"') and s.endswith('"')) or (s.startswith("'") and s.endswith("'")):
        return s[1:-1]
    if re.search(r'WebPixelRatio\.get\(\)', s):
        return 1
    if re.fullmatch(r'-?\d+', s):
        try: return int(s)
        except: return s
    if s == "true": return True
    if s == "false": return False
    return None

The routine was extended to deal with additional scalar forms, helper calls, and conditional expressions encountered in the generated bundles.

This matters because compiler output frequently represents a simple semantic value through syntax that is quite different from the source-level representation a developer would normally expect. Without normalization, the extracted repository would contain implementation details of the compiler rather than useful values.

Even so, static defaults had a clear ceiling.

A client artifact that records a variable with a default of null provides evidence that the corresponding operation expects or models that variable. It does not necessarily provide a value that can be used to reproduce the application's real behavior.

That distinction became central to the design.

7. Cross-File Correlation

One of the harder problems was that Relay does not necessarily place every relevant piece of an operation in the same JavaScript file.

The operation identifier, operation metadata, and variable definitions may arrive in different bundles or modules.

Stage 3 introduced caches to correlate them: 

CACHE_DOC_BY_BASE = {}
CACHE_VARS_BY_BASE = {}
CACHE_MODULE_BY_BASE = {}

The operation's base name served as the join key.

A variable set recovered from something resembling: 

BaseName.graphql

could therefore be associated later with information from: 

BaseName_facebookRelayOperation

This was a conceptual step forward for the project.

The extractor was no longer simply locating syntax. It was reconstructing relationships between generated artifacts that had been separated by the build process.

At the end of this stage, the repository could represent an operation with its name, doc_id, variable definitions, and inferred defaults.

But the most useful variable value might still be missing.

Static analysis could tell HarQL that a variable existed. It could often tell the system its default. It could not guarantee that the default reflected the value used by a real application session.

For that, the wire itself became the source of evidence.

8. Runtime Observation

Stage 3 added request interception alongside JavaScript response processing.

The mitmproxy request() hook filtered traffic associated with GraphQL endpoints: 

def request(flow: http.HTTPFlow):
  
    try:
        url = (flow.request.pretty_url or "")
        url_lc = url.lower()
        if "/api/graphql" not in url_lc:
            return

The parser was designed to accommodate several request encodings observed in the examined application's GraphQL traffic. It attempted JSON first and then handled form-encoded and parameter-based representations: 

def _parse_graphql_variables_from_body(req_text: str):
    """
    Robust extractor:
    - JSON dict: {"variables": {...}} or variables as JSON string.
    - JSON array: [{"variables": {...}}, ...]
    - form-urlencoded: variables=... (JSON string)
    """
    if not req_text:
        return []

    # Try JSON first
    try:
        obj = json.loads(req_text)
        if isinstance(obj, dict):
            vars_field = obj.get("variables")
            if isinstance(vars_field, dict):
                return [vars_field]
            if isinstance(vars_field, str):
                try:
                    parsed = json.loads(vars_field)
                    if isinstance(parsed, dict):
                        return [parsed]
                except Exception:
                    pass
            return []
        if isinstance(obj, list):
            out = []
            for item in obj:
                if isinstance(item, dict):
                    v = item.get("variables")
                    if isinstance(v, dict):
                        out.append(v)
                    elif isinstance(v, str):
                        try:
                            pv = json.loads(v)
                            if isinstance(pv, dict):
                                out.append(pv)
                        except Exception:
                            pass
            return out
    except Exception:
        pass

    # Fallback: form-urlencoded
    try:
        qs = parse_qs(req_text, keep_blank_values=True)
        vars_list = qs.get("variables") or qs.get("Variables") or []
        out = []
        for v in vars_list:
            try:
                parsed = json.loads(v)
                if isinstance(parsed, dict):
                    out.append(parsed)
            except Exception:
                continue
        if out:
            return out
    except Exception:
        pass

    return []

Observed values were stored in: 

OBSERVED_PARAMS = {}

and accumulated with frequency information.

This created a second body of evidence.

The static analysis side described the operation metadata exposed by the client artifacts.

The runtime side described actual operation usage and variable values observed in the application.

That distinction is significant.

A static artifact may declare a variable that is rarely used, populated dynamically, or normally supplied with a value derived from application state. Conversely, a live request contains a concrete value, but without context it may be difficult to determine which harvested operation or variable declaration it belongs to.

HarQL therefore needed a correlation mechanism that could sit between the two.

9. Static–Runtime Fusion

The most important design idea in HarQL is the combination of those two evidence sources.

Static analysis supplies operation identities, variables, and defaults.

Traffic observation supplies concrete values.

Normalization and matching establish the relationship between them.

Conceptually, the system looks like this: 

Static JavaScript Analysis
        |
        v
Operation Metadata + Variables
        |
        |                         Live Traffic
        |                              |
        |                              v
        |                       Observed Values
        |                              |
        +---------- Matching ----------+
                        |
                        v
                 Injection Rules
                        |
                        v
                Reconstructed Request

The generated dashboard implemented this through a rule layer backed by browser storage: 

const LS_KEY = 'pf_injection_rules';
let injectionRules = loadRules();

The distinction between source data and temporary substitutions was preserved through an overlay: 

let tempOverlayRules = {};

That design allowed the operator to experiment with substitutions without modifying the underlying harvested record.

The interface also included automatic candidate population: 

function autoAddObservedCandidates(){
    const candidates = collectObservedCandidates();
    const missing = candidates.filter(c=>!(c.nk in injectionRules));
    if(missing.length === 0) return;
    missing.forEach(c=>{
        addAutoRule(c.nk, c.top);
    });
    saveAutoAdded();
    saveRules();
}

The repository itself used merge semantics so that later discoveries could enrich earlier ones: 

def _merge_vars(existing: dict, newvars: dict):
    if not isinstance(existing, dict) or not existing:
        return dict(newvars) if isinstance(newvars, dict) else {}
    if not isinstance(newvars, dict) or not newvars:
        return existing
    merged = dict(existing)
    for k, v in newvars.items():
        if k not in merged or merged[k] is None:
            merged[k] = v
    return merged

This was particularly useful for variables initially discovered with incomplete defaults and later observed in live requests.

The resulting system had moved beyond inventory.

It had begun assembling enough information to construct a usable representation of an operation.

10. The Hybrid Python–Java Architecture

The next challenge was not extraction itself but integration.

HarQL needed to operate inside Burp Suite while retaining the Python-based harvesting engine that had already been developed.

The intermediate solution was a local hybrid architecture.

A Java Burp extension provided the user interface and integration point. A Python process remained responsible for harvesting and data processing. The two communicated through a local HTTP service.

The arrangement can be summarized as: 

Burp Suite
    |
    v
Java Extension
    |
    | HTTP
    v
127.0.0.1:13496
    |
    v
Python HTTP Service
    |
    v
Harvesting Engine
    |
    v
Repository / Observations / Reconstruction

The Burp interface exposed a dedicated GraphQL Harvester tab, while the local service provided repository and observation data as well as request-related operations.

The design had a practical advantage: Burp integration could be introduced without immediately rewriting the extraction engine.

It also introduced substantial operational overhead.

There were now two processes to manage, two runtimes, serialization boundaries, IPC behavior, and independent failure modes. Every interface between the components became part of the system that had to be kept stable.

The hybrid architecture solved the immediate problem, but it also made the case for a native implementation increasingly compelling.

11. The Java Rewrite

The eventual response was a full Java rewrite intended to run directly inside Burp Suite.

The public HarQL implementation was designed around Burp's Montoya API and organized the extension as a single native application rather than a Java front-end connected to an external Python service.

The reported component model included:

  • Extension.java as the entry point.
  • HttpListener.java for traffic interception.
  • MainTab.java as the primary UI container.
  • InMemoryEngine.java as the central state and processing layer.
  • GraphQLHarvesterService.java for JavaScript extraction.
  • GraphQLSchemaBuilder.java for schema-oriented inference.
  • Swing panels for repository, observation, and schema views.

The rewrite brought several architectural advantages.

Burp integration no longer depended on local IPC.

The UI was native to the host platform, using Swing components rather than generated HTML.

Rule state could be held directly by the extension instead of browser localStorage.

A schema builder was introduced to generate SDL-like structures from harvested variables and inferred scalar categories.

Interactive graph visualization was added to the interface.

The implementation also introduced safeguards around the size of JavaScript modules processed by the extractor, reducing the risk of excessive resource consumption on unexpectedly large inputs.

Request reconstruction was tied directly to Burp workflows, including integration with Repeater.

The rewrite therefore made the system more coherent from an operational perspective. It also forced several earlier experimental features to be reconsidered.

12. The Cost of Native Integration

The Python dashboard had developed in a highly exploratory environment.

Browser-side JavaScript made it inexpensive to add automatic rule population, dynamic previews, pattern-based substitutions, presets, and visual indicators. These features were useful during experimentation because the interface could change rapidly alongside the extraction logic.

The native Java implementation had different constraints.

State management became explicit. UI behavior became part of a long-lived extension. Concurrency and lifecycle issues mattered more. Features that had been straightforward in a generated HTML document could require considerably more infrastructure when expressed as persistent Java components.

Some of the earlier automation was therefore simplified or made more explicit in the native implementation.

That trade-off is important because it shows that the rewrite was not simply a feature-for-feature migration.

The engineering priorities had changed.

The earlier design favored experimentation and flexibility.

The native extension favored integration, consistency, and a smaller operational footprint.

In a reverse-engineering project, that distinction matters. The architecture that is ideal for discovering a technique is not necessarily the architecture that is ideal for packaging the technique into a dependable security tool.

At a high level, the Java implementation can be viewed as a unified processing pipeline:

The engine maintains harvested repository entries, session state, observed parameters, and injection rules.

JavaScript responses feed the static-analysis path.

GraphQL requests feed the runtime-observation path.

The resulting information converges inside the engine, where variable definitions can be associated with observed values and prepared for request reconstruction.

The architecture is materially simpler than the earlier hybrid arrangement because the core data path remains within the same process.

14. Engineering Problems That Shaped the System

14.1 The Proximity Heuristic

The first version's twenty-line window was useful only as a quick experiment.

It assumed that textual closeness implied semantic relatedness. Compiler-generated JavaScript does not consistently behave that way.

The failed heuristic established an early design rule for the project: relationships need to be inferred from module and artifact structure whenever possible, rather than from arbitrary distances in the source text.

14.2 Regex Fragility

Regex was the enabling technology behind the early system because it made rapid iteration possible.

The same choice became increasingly uncomfortable as the extractor grew.

Patterns such as: 

__d(...)
e.exports
_facebookRelayOperation
LocalArgument
$Parameters

are implementation conventions, not language-level semantics.

They work while the generated output resembles the patterns being searched.

A change in compiler templates, module wrappers, minification behavior, or internal naming conventions can therefore invalidate an extraction rule even if the underlying GraphQL semantics remain unchanged.

This is the fundamental weakness of regex-driven reverse engineering of generated code: it recognizes a representation, not the program structure that produced that representation.

14.3 IPC and Process Boundaries

The hybrid design introduced a number of concerns that had little to do with GraphQL itself.

Data had to cross a process boundary.

Requests and responses had to be serialized.

Both components had to remain alive and synchronized.

Failures had to be diagnosed across two runtimes.

The design worked, but its operational complexity was difficult to justify once the extraction engine itself had become mature enough to justify a native Burp implementation.

14.4 Automation Regression

The native rewrite also demonstrated that engineering progress can involve losing functionality.

Some browser-side automation did not carry over intact.

The reason was not that those features ceased to be useful. The implementation environment had changed, and the cost of maintaining them had increased.

This is a recurring pattern in security tooling: an exploratory prototype can tolerate convenience mechanisms that become liabilities once the same mechanism is embedded in a persistent extension.

14.5 Write-Heavy Persistence

The Python implementation regenerated repository JSON and HTML output as discoveries arrived.

That is simple and transparent, but it creates unnecessary serialization work as the dataset grows.

A larger deployment would benefit from a storage layer that separates event ingestion from materialized views, or at least updates only the affected records rather than rewriting complete representations.

The original design was adequate for rapid experimentation but not ideal as a foundation for very high-volume harvesting.

14.6 Static Defaults Are Not Runtime State

A variable definition and a usable request value are different things.

A compiler artifact may state that a variable exists and provide null as its default. The live application may almost never send null.

That discrepancy is one of the reasons runtime observation became a first-class component rather than an auxiliary feature.

The broader lesson applies to reverse engineering beyond GraphQL: static artifacts frequently reveal the contract, while runtime traces reveal the operational behavior.

A useful reconstruction system benefits from both.

15. What HarQL Actually Reconstructs

It is important to be precise about what the system recovers.

For the Meta client artifacts examined, HarQL can reconstruct useful operation metadata: operation names, observed doc_id values, variable definitions represented in the client artifacts, inferred defaults, and, where observed, concrete runtime values.

That is enough to build a substantial operational picture of the client's GraphQL surface.

It is not equivalent to recovering the server's complete GraphQL schema.

The distinction matters.

Client-side variable definitions do not reveal the full server-side GraphQL type system or object model.

They do not establish every field exposed by a type.

They do not recover resolver behavior.

They do not enumerate every interface or union.

They do not provide an authoritative representation of the server-side GraphQL schema equivalent to querying the service's own schema through its introspection system.

The schema-oriented output generated by the Java implementation should therefore be regarded as inference derived from client artifacts, not as a ground-truth reconstruction of the backend schema.

That distinction is essential when evaluating the scope of the technique.

16. Static Analysis and Runtime Evidence as Complementary Sources

The strongest aspect of the HarQL model is not any individual regex or parser.

It is the relationship between different evidence sources.

Static client analysis can expose operations that may never appear in a particular browsing session.

Runtime observation provides concrete values and real invocation patterns but only for behavior that actually occurred.

Static client artifacts can expose a broader set of operations than those exercised during a particular session, but they may not contain every piece of information required for reconstruction.

Runtime traffic provides concrete evidence about operations and values actually observed, but it is inherently limited to the application's observed execution paths.

Using both allows the system to compensate for the weaknesses of each.

A useful way to think about this relationship is: 

Static Evidence
  ├─ Operation Identity
  ├─ Variable Presence
  └─ Default Information

             +

Runtime Evidence
  ├─ Concrete Values
  ├─ Value Frequency
  └─ Observed Usage

             ↓

       Correlated Model
             ↓
     Reconstructable Request

That model is more general than the particular extraction techniques used by HarQL.

It describes a broader reverse-engineering strategy in which code artifacts and runtime behavior are treated as complementary evidence rather than competing sources.

17. Limitations

HarQL's approach has several important limitations.

Target specificity

The extraction logic is strongly tied to the module conventions and Relay-generated client artifacts observed in the examined Meta applications. A different GraphQL client may expose its operation metadata through entirely different structures.

Regex dependence

Much of the audited extraction pipeline remains based on textual patterns. Changes in generated JavaScript can therefore break individual extractors.

Runtime dependence

Static extraction can identify operations and client-side variable metadata without necessarily providing values suitable for reproducing the application's observed requests. Representative traffic remains important for reconstruction.

Storage model

Repeated JSON and HTML rewrites are convenient for a prototype but become less attractive as the repository grows.

Schema scope

The recovered client-side information should not be confused with the complete server-side GraphQL schema or type system. The system focuses on the client-visible operation surface and the data required to exercise it.

Identity

doc_id is a useful identifier but not necessarily a complete identity model for an operation. An operation fingerprint derived from structural properties can provide stronger semantics and may remain meaningful even when identifiers change.

Validation

A robust production system would benefit from quantitative measurements covering extraction accuracy, false positives, false negatives, throughput, memory consumption, and reconstruction success rates. Those measurements were not a formal part of the early development process.

These limitations are not peripheral details. They define the boundaries within which the current approach should be interpreted.

18. Why AST Becomes the Natural Next Step

Regex remains attractive because it is lightweight and fast.

It is also fundamentally tied to textual representation.

An AST-based extractor operates at a different level.

Instead of matching the textual form of module wrappers and generated artifacts, it can reason about JavaScript syntax such as declarations, call expressions, assignments, object literals, function scopes, and property relationships.

That distinction becomes increasingly important as JavaScript generated by modern toolchains changes shape while preserving the same underlying semantics.

The planned next generation of HarQL therefore moves toward semantic parsing with the Meriyah JavaScript parser.

The expected benefit is not simply greater tolerance of changes in minification and generated-code layout.

An AST-oriented architecture can support a richer analysis model:

  • identify module boundaries from syntax rather than textual layout;
  • trace assignments and references;
  • associate exports with the structures that produce them;
  • reason about generated object literals;
  • derive stronger operation fingerprints;
  • correlate artifacts through structural identity rather than only naming conventions;
  • provide a foundation for deeper inference layers.

The conceptual progression is better expressed as a change in abstraction: 

Textual Pattern Recognition
            ↓
Module-Aware Extraction
            ↓
Static + Runtime Correlation
            ↓
Semantic JavaScript Analysis
            ↓
Structural GraphQL Modeling

The value of the AST direction lies in its ability to make the extractor less dependent on how the compiler happens to spell a structure in a particular release.

19. Conclusion

HarQL began with an observation that is easy to state but difficult to operationalize: if a browser-based client can issue a particular GraphQL operation, the client implementation must retain enough information to construct the corresponding request.

The first prototype demonstrated that operation identifiers could be located with simple textual heuristics. Subsequent work established reliable relationships between identifiers and Relay operation modules, recovered variable definitions from compiler-generated artifacts, and introduced cross-file correlation where the build pipeline had separated related pieces of information.

Runtime observation added something static analysis could not reliably provide: concrete values used by the application in practice.

Once those sources were combined, HarQL could represent more than a list of hidden identifiers. It could maintain a correlated model of operations, variables, defaults, and observed values, creating the basis for request reconstruction.

The hybrid Python–Java design then addressed Burp integration without discarding the existing harvesting engine. Its limitations eventually led to a native Java implementation with tighter platform integration and a more centralized architecture.

The most significant lesson from the project is therefore architectural rather than syntactic.

The useful information is distributed.

Part of it can be present in compiled client artifacts.

Another part appears in runtime traffic.

Neither source is complete in isolation, but together they provide considerably more visibility into the client-visible GraphQL operation surface of the examined application.

HarQL's current limitations are equally instructive. Regex-based extraction remains dependent on implementation conventions, storage is not optimized for unrestricted scale, and variable-level reconstruction must not be mistaken for complete schema recovery.

Those constraints point toward the next stage of the work.

A parser that understands the JavaScript structure itself can provide a more durable foundation than a growing collection of textual patterns. From there, stronger operation identity, structural fingerprints, artifact correlation, and deeper GraphQL inference become engineering problems rather than speculative ideas.

The significance of HarQL lies in that progression.

It demonstrates that the absence of server-side GraphQL introspection does not necessarily eliminate the information retained by a particular client implementation for constructing its GraphQL operations. In many systems, the information required to communicate with the backend has already been distributed across the client artifacts and the runtime behavior of the application.

In the context examined here, the reverse engineer's task is to recover that distributed client-side knowledge, establish the relationships between its parts, and represent it in a form that can be analyzed and tested.

That is the underlying problem HarQL was built to investigate.

Research Status

This article documents the engineering evolution of HarQL and describes implementation behavior, architectural decisions, observed limitations, and planned directions based on the development history of the system.

The article distinguishes client-side reconstruction from authoritative server-side schema recovery. The reconstructed information should therefore be interpreted as client-visible operational evidence rather than as a complete representation of a backend GraphQL schema.
